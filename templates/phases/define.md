# DEFINE 相位

你在**定义问题**,不是解决问题。需求模糊时写不出可执行的 AC,而此时 agent 的行为是可
预测的:**编一条"AC1: 用户体验良好"出来凑格式**,然后整套判定建立在一条假标准上。
这一相位就是为了不让那件事发生。

## 先分清你面对的是哪一类模糊

| 类型 | 答案在哪 | 出口 |
|---|---|---|
| 描述不清 | 人的脑子里 | `mission_ask` |
| 事实不明 | 代码/环境里 | **自己去读**;要跑要量才知道的,进 PLAN 排一个 spike |
| 方案未定 | 不在任何人脑子里 | 自己造两三个选项,带推荐答案去问 |

**找事实是你的活,做决策是人的活。** 拿"旧 API 到底用在 3 处还是 300 处"去问人是浪费
额度 —— 人也不知道。很多"模糊"是没看代码造成的:先读,读完还剩的才值得问。

提问的闸门(轮次、每轮上限、必须带推荐答案、每轮要结账)由 L0 强制,细则见
`mission_ask` 的工具说明,当前用量见 State Card。这里只说一条判断:
**只问那些答案会改变完成条件或方案分支的问题**,改变不了任何东西的别问。

- ✅ "『快一点』指首屏渲染还是登录接口响应?接口 p95 现在 800ms。推荐:按接口 p95,目标 300ms"
- ❌ "能详细说说你的需求吗?"

问不完就说明这个需求该退回给人重新描述 —— 连环追问二十条,比直接说
"这个需求我没法定义,请换个说法"更糟。

## 完成条件(doneWhen)—— 这一段决定后面所有事

写"满足什么就算做完了",一条一个 id。用人话写,但**每条都要能判真假**。

PLAN 会把每条翻译成一个能跑出退出码的 verify 分支。机器两个方向都查:漏一条冻结不了,
夹带一条(AC 不覆盖任何 doneWhen)同样冻结不了。所以写的时候就按"这条要怎么跑出退出码"
来想 —— 想不出来的,现在就该继续问或者缩小范围,不要留给 PLAN。

- ✅ DW1: 旧的 session 中间件不再被任何路由引用
- ✅ DW2: 现有登录用例全绿,且不需要改断言
- ❌ DW3: 鉴权体验更好(判不了真假,写不成退出码)
- ❌ DW4: 顺便把日志也整理一下(这是另一个 mission)

**清单要完整但要短。** 它是人要逐条批准的东西,也是你后面唯一被允许追的目标。

## 验证接缝(verifySeam)

一句话说明打算在哪一层验证:优先用**已有的**测试设施,用**尽可能高**的那一层。

选错接缝的代价原本要到冻结基线那一关才显现 —— 那时整轮 PLAN 已经烧完了。写在这里,
人才有机会说"不对,这个用契约比对更省事"。

- ✅ "已有集成测试 test/auth/*.test.ts,新增一个用例"
- ✅ "grep 计数:旧 API 的调用点数必须降到 0"
- ❌ "写测试"(哪一层?新的还是旧的?)

## 禁止

- 在这里设计方案、拆任务、写 AC。那是 PLAN 的活。
- 把"待调研""看情况"写进 goal 或 doneWhen —— 那是把模糊原样传给了 PLAN。
- 自问自答:`mission_ask` 的回答会直接出现在工具结果里,拿到之后再决定追问还是交定义,
  不要自己猜一个答案往下做。
