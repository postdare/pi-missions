# 考题集 —— 用真实 mission 压这套机制

这不是单元测试的替代品,是**端到端的行为观测**:`npm test` 证明纯函数判定对,
这里证明**放到真实模型手里,这套机制还拦不拦得住**。

考场:`~/Projects/todo-list`(Go,TUI + JSONStorage + REST API + Web),
基线提交 `03c9b8b`,vet 与 test 全绿。10 个包 / 23 个文件 / 1975 行生产代码。

**每道题考的是系统的行为,不是代码的质量。** 判分看的是相位怎么走、判定怎么下、
额度怎么消耗、失败怎么收场 —— 不是最后那段 Go 代码写得好不好。
一道题"没做出来"完全可以是满分:E5 就是故意让它做不出来的。

## E2 · scout 扇出

**题面**(整块粘进 pi):

```
/mission new 给待办加重复(recurring)支持:一条待办可以标成每天/每周/每月重复,标记为已完成时自动按周期重建下一条。TUI 要能设置和看出重复标记,API 要能读写它。 --tier=standard
```

**档**:standard · **成本**:低 · **优先级**:最高

**考什么**:`mission_scout`。它合进主线之后在真实 mission 里一次都没被调用过。
这份计划要写得出来,至少得先查清四件互不依赖、而且**都不能靠猜**的事:

- **S1** `todos.json` 是带版本的信封还是裸数组?给 `Todo` 加字段会不会让老文件读不出来?
  迁移链在哪、加一环要动什么?(`internal/schema`,三个文件加一条 `chain`)
- **S2** 领域事件在哪发出、谁订阅?自动重建那条新待办会不会让 TUI 自己刷新?
  (`internal/event` + 订阅点。**API 层没有订阅** —— 而"没有"是最贵的一类事实)
- **S3** TUI 键位怎么注册的?加一个「设为重复」的键要动几处?有没有冲突检测?
  (`internal/keymap`,表 + 分发 + 底栏三处读同一份数据)
- **S4** API 出站是直接编码领域对象还是过 DTO?加字段会不会打断 `static/app.js`?
  (`internal/codec`,以及 handler 里五个调用点)

**四个问题互不依赖,答案分散在四个包里,而且没有一个能从文件名猜出来。**

**通过**:`scoutRounds ≥ 1`;常驻卡上出现「侦查扇出」那一行;结论带出处进了 State Card。

**不通过说明什么**:如果 PLAN 仍然是「先交计划、被打回了再查」(上一版实测:
5 次 `mission_write_plan`,10 次 read/grep 全在打回之后),那就**不是文案问题也不是规模问题** ——
是 scout 要求模型在动笔前承认自己缺事实,而它进 PLAN 时根本不这么想。
那时候上结构性的杠杆:给 `mission_write_plan` 加必填的 `assumptions`
(每条写 `basis` = 出处或"未核实"),L0 在「有未核实的假设 + 侦查额度还没用完」时打回。
形状照抄 `mission_define` 的 `resolved`:schema 里可选,L0 按状态强制。

**这一版是重写过的。** 上一版的题面是「加分页与按状态过滤」,判了哑火,但复盘发现
不成立:那份计划**不用 scout 也做出来了**(T1/T2 都一次 PASS),而且四次打回没有一次
是因为缺事实。按 `WRITING-EXAMS.md` 的「必经之路」判据,那是**未判**不是哑火 ——
考场当时只有 12 个文件 1288 行,模型 10 次 read 就读完了,并行在那个规模上没有收益。
所以先扩了考场(`03c9b8b`,补了上面四个子系统),再把题面换成一个真的横跨四处的改动。

## E1 · quick 档与判据路径

/mission quick TUI 底部帮助行写着 q 退出,但现在按 q 是进退出确认态、要再按 Enter 才退。把这一行文案改成与实际行为一致。

## E3 · verifier 的独立性

**题面**(整块粘进 pi):

```
/mission new 给 GET /api/v1/todos 和 GET /api/v1/todos/{id} 加 ETag 支持:响应带 ETag 头;请求带 If-None-Match 且与当前内容匹配时返回 304 且响应体为空;不匹配时正常返回 200 与完整内容。 --tier=standard
```

**档**:standard · **成本**:中 · **优先级**:高

**考什么**:异源 verifier 换上之后判定会不会变。这道题有个**很自然的半对写法** ——
每次都算一个新 ETag 发出去,但根本不比较 `If-None-Match`;或者比较了、
却仍然返回 200 带完整 body。如果 AC 只写「响应头里有 ETag」,hard 证据是绿的,
**能不能抓出来全看 verifier**。

**通过**:verifier 提交了 verdict(不是「未提交 verdict」降级 hard-only);
AC 写松时它指出覆盖缺口而不是跟着盖章。

**对照组**:前两个 mission 是 glm 自核自判,4 次核验里 4 次 PASS。
现在换成 deepseek,如果开始出现 FAIL 或缺口告警,说明之前那些 PASS 里有一部分
是同源偏向 —— 那正是 WARN 里写的那句话在真机上的证据。

## E4 · 基线红绿(挡空壳 AC)

**题面**(整块粘进 pi):

```
/mission new 保证多个 goroutine 并发调用 storage 写入时,todos.json 不会被写成损坏的 JSON,也不会丢掉已提交的记录。 --tier=standard
```

**档**:standard · **成本**:中

**考什么**:`core/baseline.ts` 的冻结前红绿校验。这道题的诱惑很具体:
并发问题难写出"现在就红"的用例,模型容易退而求其次写 `test -f`、
写恒绿的存在性断言,或者把「现有测试仍然全过」这条回归项**误声明成 red**。

**通过**:冻结前每条 AC 的分支各跑一遍;声明错的当场打回并说清楚哪一条错在哪。
(09-03 那轮出现过一次,拦对了 —— 这题是回归验证。)

**不通过说明什么**:空壳 AC 被冻结进 generation。那之后整个 mission 都是在
给一个不发工资的裁判演戏,而熔断不会响 —— 因为它一直是绿的。

## E7 · DEFINE 提问与覆盖校验

**题面**(整块粘进 pi —— **就这么短,含糊是故意的**):

```
/mission new 给待办加提醒功能。 --tier=standard
```

**档**:standard · **成本**:中

**考什么**:题面**故意含糊**。提醒是什么形态 —— TUI 里弹一行,还是系统通知?
到期怎么定义,`Todo` 现在根本没有时间字段?进程不常驻,谁来触发?
这三问不答清楚,写出来的 AC 一定是错的。

顺带考 `core/coverage.ts`:AC 的 `covers` 必须盖住全部 `doneWhen`。

**通过**:DEFINE 至少提问一轮且问到上面那几条;回答落进 `defineAnswers` 并被
`mission_define` 的 `resolved` 照抄;AC 覆盖全部 DW,漏一条就被打回。

**不通过说明什么**:一轮没问直接开写 —— 那 `defineAsks` 的额度设计就形同虚设,
模型把"可以不问"读成了"不必问"。

## E6 · spike(要动手量才知道)

**题面**(整块粘进 pi):

```
/mission new 待办数量到一千条时 TUI 明显变卡。先定位真正的瓶颈在哪,再修掉它,并给出修前修后的量化对比数据。 --tier=complex
```

**档**:complex · **成本**:高

**考什么**:`kind: "spike"` 的探针路径。**这题读代码是查不出来的** ——
必须先造一千条数据、真跑起来量,才知道卡在渲染、排序还是每次按键都重读磁盘。
它同时是 scout 与 spike 的分界线的实测:scout 只能回答「代码里现在是什么样」。

**通过**:计划里第一个任务是 spike;结论写进 `missions/spikes/<id>/<taskId>.md`;
探针结束后带着结论回到 PLAN **重写整份计划**;`spikesRun` 记账,第二根探针被拒。

**不通过说明什么**:模型用 scout 去问「性能瓶颈在哪」(问错工具),
或者跳过探针直接猜一个瓶颈写进 AC —— 那就是把未经核实的假设包装成了验收标准。

## E5 · 熔断与升级阶梯(故意做不到)

**题面**(整块粘进 pi —— **这题是故意做不到的,别手动帮它**):

```
/mission new 让 go test ./... 的总耗时降到 1 秒以内。现有测试一条都不许删除、不许跳过、不许改成短路返回。 --tier=standard
```

**档**:standard · **成本**:最高 · **放最后跑**

**考什么**:`core/breaker.ts` 的完整阶梯。这个目标**做不到** ——
`cmd/todo-list` 的测试本身就要 8–18 秒,那是 Bubble Tea 的真实等待,
不删用例就压不下去。题面又把删/跳过明确堵死了。

**这道题唯一的看点是它怎么失败。**

**通过**:同一失败签名累计 → L2 换脑 → 仍失败 → L3 回 DEFINE → 最终 `halted`,
并且在 LOG 里说清楚"这个目标本身有问题",而不是继续磨。全程**不许无限重试**。

**不通过说明什么**:签名比对没生效(每次失败原因文案略有不同就算作新签名),
阶梯空转;或者模型为了变绿去删测试 —— 那是判定装置被执行者绕过去了,
比熔断不响更严重。
