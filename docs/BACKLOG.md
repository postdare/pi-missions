## 子 agent 的执行详情没有入口

**症状**:进程内的子 agent(独立核验 verifier、并行侦查 scout)跑起来之后,
人在 TUI 里看不到它到底做了什么。真机原话:「我现在完全看不到独立核验的进展」。

**现状**:数据一直都在,只是没有一个页面通向它。

- `CHECK.json` 的 `verifier.trace` 是完整轨迹(浏览了哪些目录、读了哪些文件、第几轮),
  真机上一次核验是 11 轮、22 次工具调用,轨迹三十多行。
- 常驻卡现在会印状态、时长、轮数、调用数和**当前**动作一行(`dashboard.ts`
  的 `checkProgressLines`,已修)—— 但那只是最新一条,看不到全程。
- `status-view.ts` 里只在判断"要不要给转向按钮"时碰了一下 `verifier.status`,
  **一行轨迹都没渲染**。
- scout 的逐路结论在工具块里,展开才有出处;而工具块会随对话滚走。

**为什么要紧**:这两个子 agent 是判定链上最贵也最不透明的一环。
`toolCalls: 0` 的核验和 `toolCalls: 22` 的核验在旧界面上长得一模一样,
而前者意味着 I3 当轮是空的 —— 人分不出来,就等于没有独立核验这回事。

**大概往哪做**:`/mission status` 的状态页加一个「核验轨迹」段,
读 `CHECK.json` 的 `trace`(结束后读归档的 evidence);scout 的历史结论
同理可以从 `state.scoutFindings` 取,它本来就落盘了。两者都是只读渲染,
不动判定。

## 任务越界 → 核验超时 → I3 静默失效

**症状**:T1 声明范围是 `internal/todo`(领域层),实际改了 11 个文件,
横跨 T1–T4 四个任务的地盘(codec、storage、api/handler、tui、keymap)。
随后独立核验跑满 300 秒超时、23 轮 38 次工具调用,降级 hard-only;
hard 证据全绿,判 PASS。

**因果链**:越界 → 核验面积是本该面积的四倍 → 超时 → **这一轮 I3 是空的**
→ 而 hard 全绿就放行。**改动越大、风险越高的那次,反而越拿不到独立核验。**

**这条推翻了此前的判断。** 越界现象已观测三次(还有一次是 restful-api 的 T1
干了 T2 的 web 页),之前判定"代价只是理论上的失败粒度,等真实损失再动"。
损失到了,而且比预期严重:丢的不是粒度,是判定权外置本身。

**三条路**:

1. 调大 `verifierTimeoutMs`(默认 300000)。治标 —— 曲线不变,只把断点推后,
   而每任务十分钟的核验会压垮循环成本。
2. 计划声明 `tasks[].touches`,闸门强制。治本但强硬:planner 要预判文件清单,
   猜错就被自己的计划锁死。
3. **超时不再等于放行**:判 `inconclusive` 而不是降级 hard-only 后 PASS。
   最贴合这套系统的哲学(判不出来就别判),而且不要求 planner 预判任何东西 ——
   压力落在"谁改得大谁去拆"。代价是大改动会反复无结论,而连续 3 次无结论停机。

倾向 3 + 1 的组合。但这动 `core/verdict.ts` 的判定逻辑,只有一个样本,先等第二次。
