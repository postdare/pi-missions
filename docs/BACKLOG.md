## pi 自己的 confirm/select 关掉时,焦点同样收不回来

**症状**:与「弹出层关掉焦点还赖在常驻卡上」同一个病(那条已修,见 git),
只是入口不同 —— 已修的是 widget 自己开的两个页(`/mission status`、动作原文),
`runtime.ts` 的 `afterOverlay()` 在它们的 promise `finally` 里收焦点。
但 pi 自己弹的 confirm / select / input 走的是 `custom-depth.ts` 包的那一层,
**没有人在它们关闭时通知 runtime**。焦点若正好落在常驻卡上,同样会僵住。

**为什么还没修**:真机上没踩到过 —— 焦点在卡上时人一般直接按 Esc,
而不是去触发一个 pi 的 confirm。列在这儿是因为病因清楚、代价明确,不是猜的。

**大概往哪做**:`custom-depth.ts` 在 depth 归零时回调一次,runtime 订阅它,
`afterOverlay()` 的两个调用点就可以撤掉(那时所有弹出层走同一条路)。
代价是多一个订阅口子 —— 等真踩到再说。

## 独立核验的看板挤在常驻位置,而且「独立核验」这四个字出现两遍

**症状**(真机原话:「这样完全不懂在干啥」)。展开后输入框下面长这样:

```
◆ 判定 1/5 · T2 TUI:添加/编辑流程接入提醒输入步 · 37min 26.8k tok · mission-bb6ba7f8
  独立核验 1m4s · 脚本 1 项
  独立核验 T2 a=1 · 1m3s · 4 轮 · 10 次调用    ↑↓ 选 · ↵详情 · esc 收起
    读取 …/todo/remind.go
    完成第 3 轮核验
    读取 …/tui/tui.go
    搜索 m.err|\.err =
    完成第 4 轮核验
    搜索 pendingRemind
  ▸ 读取 …/tui/tui_test.go
    10-16/16
```

**病因一:两个不同的东西共用一个标签,还并排。**

- 第 2 行是常驻卡的 CHECK 进度子行,标签取 `dashboard.ts` 的
  `STAGE_LABELS["running_verifier"]` = 「独立核验」,时长是**整个 CHECK** 的。
- 第 3 行是看板的标题行,标签取 `board.ts` 的 `boardTitle()` = 「独立核验」,
  时长是 **verifier 子 agent 自己**的。

两个时长差 1 秒(1m4s / 1m3s),看起来像同一件事印了两遍、还印错了一个。
实际是「CHECK 走到了核验阶段」和「核验这个子 agent 在跑」两件事。

**病因二:展开态在**常驻**位置铺了 10 行。** CLAUDE.md 写着那几行「不是消息,是永久占位」,
所以定的规矩是单行密排。看板展开违反的正是它自己那条前提 —— 它借走了整块常驻空间,
还夹在 pi 的 statusline 中间。

**病因三:轨迹是流水账,没有结论。** 「读取 xx / 搜索 yy / 完成第 N 轮核验」交替出现,
看得出它**在动**,看不出它在核**哪一条 AC**、核出了什么。而人盯着这块看的时候,
想知道的恰恰是后者。

**为什么要紧**:这块 UI 存在的理由就是「独立核验不再是黑盒」(见上一条待办的由来)。
现在它把黑盒换成了一屏看不懂的流水 —— 目的没达到,却付了常驻十行的价。

**大概往哪做**(用户倾向:**做成弹窗**):

1. 收起态保持现在这一行(「还活着、在动什么」,那一行是有效的),
   ↵ 改成打开 `ctx.ui.custom` 的整页 —— 和 `/mission status`、评审页同一种壳,
   高度是临时的,爱铺多少铺多少。`board-detail.ts` 已经是这个形状,只是现在只装一条轨迹。
2. 先把两个标签拆开也值一做,那是个小改:CHECK 阶段那行叫「核验中」或直接并进上一行,
   看板标题保留「独立核验」。**别让同一个词在相邻两行指两个东西。**
3. **把结论显出来,别只显轨迹。** 结论已经有了,只是这块 UI 没读它 ——
   归档的 `semi` 证据里 `raw` 就是核验结论的正文,`stdout` 是完整轨迹。真机样本(E7 T3):

   > 实现与 AC 语义一致:(1) `sweepReminders(tui.go:155)` 在提醒到点且未完成、未 fired 时
   > 设置含 `t.Title` 的 `m.banner`…(3) `fired` map 保证同一提醒每次 tick 只触发一次…
   > 单元测试 TestRemindFires/TestRemindFiresOnce/TestDoneTodoNoRemind **未被削弱**;
   > 唯一可挑剔点(同一时刻多个提醒到点,banner 单值只保留最后一个)不在该 AC 的测试语义内,
   > 不足以判 fail。

   这段话才是人要看的东西 —— 它带着 `file:line`、说清了为什么不判 fail、还点出了一个
   它选择放过的缺陷。而看板现在只印「读取 …/tui/tui.go」这类流水。
   跑动时手上只有 `CheckVerifierProgress`(平铺 `trace` + `activity`),结论要等它提交;
   **所以弹窗页天然分两段:跑动中显轨迹,结束后显结论**,后者从归档的 evidence 读。

## 子 agent 的执行详情没有入口

**症状**:进程内的子 agent(独立核验 verifier、并行侦查 scout)跑起来之后,
人在 TUI 里看不到它到底做了什么。真机原话:「我现在完全看不到独立核验的进展」。

**现状**:数据一直都在,只是没有一个页面通向它。

- `CHECK.json` 的 `verifier.trace` 是完整轨迹(浏览了哪些目录、读了哪些文件、第几轮),
  真机上一次核验是 11 轮、22 次工具调用,轨迹三十多行。
- 常驻卡现在会印状态、时长、轮数、调用数和**当前**动作一行(`dashboard.ts`
  的 `checkProgressLines`,已修)—— 但那只是最新一条,看不到全程。
- `status-view.ts` 里只在判断"要不要给转向按钮"时碰了一下 `verifier.status`,
  **一行轨迹都没渲染**。
- scout 的逐路结论在工具块里,展开才有出处;而工具块会随对话滚走。

**为什么要紧**:这两个子 agent 是判定链上最贵也最不透明的一环。
`toolCalls: 0` 的核验和 `toolCalls: 22` 的核验在旧界面上长得一模一样,
而前者意味着 I3 当轮是空的 —— 人分不出来,就等于没有独立核验这回事。

**大概往哪做**:`/mission status` 的状态页加一个「核验轨迹」段,
读 `CHECK.json` 的 `trace`(结束后读归档的 evidence);scout 的历史结论

不动判定。

## verify.sh 的 cwd:R2(临时目录)还只有拦截,没有根治

**已修的那半**:「cd 到脚本自己所在的目录」(R1)现在由 L0 在冻结前**直接删掉**,
不再打回让模型重写 —— `core/verify-script.ts` 的 `autoFixVerifyScript()`,
剥离写进 LOG(`verify.sh 自动剥离 N 行…`)。

**为什么从"拦"改成"删"**:三次真机事故,三次同一行。
`templates/phases/plan.md` 里写了警告,L0 的打回意见把正确答案(什么都不写)
明说了两遍 —— E7(09-04)照踩,09-05 另一个 mission 又踩,**不同会话、不同题目、
同一个 `cd "$(dirname "$0")/.."`**。不是没读到,是这个写法在 shell 里的肌肉记忆
压过了提示。文案再加一遍没用(同 E8 的教训)。

**仍然缺的**:

1. **R2(cd 进 mktemp 目录)没有自动修,也不该有** —— 在临时目录里干活可以是正当的
   (放产物、隔离 HOME),删了就是把一个可能正确的脚本改坏。那个文件立着
   「宁可漏判,不可误判」的纪律,自动改脚本会让误判从"能申辩"变成"无声改坏"。
   R2 只能继续打回。**如果 R2 也开始反复栽**,那要想的是换一种表达方式
   (比如给模板一个现成的 `run_in_repo` 函数),不是放宽自动剥离。
2. **误判样本仍然是 0**。拦截是启发式字符串检查,一条合法的 `cd "$REPO/subdir"`
   会不会被误伤,还没有数据。现在多了一层风险:R1 误判不再只是打回,是**直接删行**。
   删的条件收得很紧(只删 R1、且整行只有这一条 cd),但样本仍然是 0。

## ~~任务越界 → 核验超时 → I3 静默失效~~ · 已订正,病因不是越界

**这条当初的因果链是错的,留着是为了记住怎么错的。**

原判断:T1 改了 11 个文件横跨四个任务的地盘 → 核验面积四倍 → 超时 → I3 空掉。
听起来严丝合缝,而且我拿它推翻了自己"再等等"的立场。

后面四轮的实测把它否掉了:

| | 耗时 | turns | toolCalls | diff |
|---|---|---|---|---|
| T1 | **300s 超时** | 23 | 38 | 11 文件 |
| T2 | 225s | 21 | 33 | **+1 文件** |
| T3 | 232s | 14 | 24 | — |
| T4 | 236s | 22 | 40 | — |
| T5 | 68s | 8 | 12 | 纯回归 AC |

**T2 的 diff 只有一个文件,核验照样 225 秒。** 核验成本不是 diff 的函数 ——
每次 CHECK 都开全新的 AgentSession,从零把仓库摸一遍去核冻结的 AC,
跟这次改了多少无关。三次实质核验挤在 225–236 秒这条 11 秒宽的带子里,
而旧阈值正好压在 300:余量 30%,调用次数多几次就翻车。T1 就是那一次。

**真病因是标定错误,不是越界。** 修法见下,已落地。

越界本身仍然存在(观测三次),但它的代价回到原来的判断:丢失败粒度,
理论上的。**没有证据之前不要给一个现象配一条听起来顺的因果链** ——
两个真实观测拼在一起,不等于其中一个导致了另一个。

**已修**:`verifierIdleMs`(默认 120s)+ `verifierCeilingMs`(默认 900s),
按静默掐而不是按总时长,判定在 `core/verifier-budget.ts`。
干活的核验不再被误杀,真卡住的从 300 秒提前到 120 秒。
